# 自定义主题扩展能力评估报告

- 初评：2026-11-11 · 复评：2026-11-12（见 §12，与初评冲突时以 §12 为准）
- 范围：DiPlay 取景窗「自定义主题」（theme.json schema 1）的扩展能力上限
- 性质：能力评估与决策参考，**不含实现承诺**；文中所有数据能力均已对照当前代码核对
- 目标：回答两个问题——**引擎最多能扩展出哪些行为能力？用户最终能做到什么效果？**

---

## 0. 一句话结论

主题可以从“静态皮肤 + 循环动画”扩展到 **“数据驱动 + 事件反应 + 场景切换 + 编排动画”**，观感接近成品车机主题引擎；但受真实数据限制，**道路限速、多车道、充电/电量、路况天气**不能作为能力基础（挡位/油量待探针确认）。

最大可靠能力建立在：**车速、转速、导航转向、歌曲、时间、昼夜、续航（已实测）**。

> 复评补充（2026-11-12）：能力上限不变，但**自定义主题没有数据启动权**——车机实测：内置主题仪表随车速动、
> 导入的自定义主题不动（§12.2）；落地顺序也要改，详见 §12；一句话路线见 §12.11。

## 1. 现状基线

| 能力 | 现在支持 |
|---|---|
| 图层 | image、brush（linear/radial/sweep）、shape、text（单行左对齐）、gauge（speed/rpm）、live（nav / card112 / eta / song） |
| 通用属性 | `z`、`dst` 绝对像素、`alpha`、`scale`、`fit` |
| 条件 | `visibleIf`：车速/转速区间、是否 Apple 完整地图 |
| 动画 | `alpha / x / y / scale / rotation`，循环，多动画叠加 |
| 数据 | 仅仪表能用 speed/rpm；文字是静态的 |
| 分发 | 目录扫描、设置页选择、双指左右切换、WPF 制作器预览/推送、静态审计脚本 |
| 主题切换 | 全屏“正在切换”提示 + 互斥门 |

## 2. 数据现实（决定能力上限）

### 2.1 稳定可用（A 级）

| 数据 | 来源 | 频率 | 备注 |
|---|---|---|---|
| 车速 | vendor 属性 `0x11600207` | 150 ms | 与内置仪表同源 |
| 转速 | `0x11600305` | 150 ms | |
| 总里程 | `0x11600204` | 150 ms | 已实测：43520.1 km |
| **续航** | `0x11600308`（RANGE_REMAINING） | 150 ms | **已实测可用：153.0 km**（实车报告，599 条属性清单含该 ID） |
| 转向指引 | `0x5201 / 0x5202` | 事件 | 图标、环岛出口、距离、路名、当前路、出口名、到达时间、剩余时间/距离 |
| 歌曲 | Now Playing 流 | 事件 | 歌名、歌手、副标题、历史 |
| 昼夜 | 车灯 `0x11400E10`（1 s）+ CarPlay 夜间模式 | 1 s | 已有内置 DAY_NIGHT 主题在用 |
| 时间 | 系统时钟 | 实时 | |
| Apple 完整地图标记 | 内部状态 | 实时 | |

### 2.2 有条件（B 级，不能作为核心依赖）

| 数据 | 情况 |
|---|---|
| 车道指引（`0x5204`） | 模型存在（`BydLaneGuidance`），但只在手机推送且导航流激活时才有；时有时无，只适合“有数据时显示”的装饰 |
| CarPlay 连接状态 | 可做等待/断连画面 |
| 导航中/静止 | 由指引或车速推断，可靠 |

### 2.3 候选待验证（下一轮实车探针，先只读、不做 UI）

| 数据 | 候选 ID | 读取通道 | 说明 |
|---|---|---|---|
| 油量 | `FUEL_LEVEL = 0x11600309`（float） | `getFloatProperty` | 与续航同族、同通道；汽油车大概率在册，但**在册 ≠ 可用** |
| 低油量 | `FUEL_LEVEL_LOW = 0x11200305`（bool） | `getBooleanProperty` | 可选，用于“低油量”提醒 |
| 挡位 | `GEAR = 0x11400400`（int） | `getIntProperty` | 与 float 不同通道；本车挡位由 MCU 绘制，可能未注册 |

> 教训来自转向灯：同族的 `0x11400E10` 大灯可用，但 `0x11400E02` 雾灯、`0x11400E03` 双闪 `available=false`。**每个属性都必须单独查 `isPropertyAvailable`，不能按族推断。**

**探针实现要点**：
- `CarLampSource.readFloatProperty()` 已经内置 `isPropertyAvailable` 检查（不可用返回 `NaN`），所以油量探针只需加一个 PID 常量 + 一个 `readFuel()`，**不会误导成 0.0**；
- 挡位需要新增 `getIntProperty` 通道（目前只有 float 通道），且本车挡位由 MCU 绘制，注册概率低；
- 日志挂在 `CarDataMonitor` 的 5 s 行里，跑一次实车即可定论；
- 量纲注意：AOSP `FUEL_LEVEL` 文档单位是毫升，车厂也可能返回升或百分比，读到值后先看数量级再定单位。

**验证方法（一次实车会话即可）**：
1. 用探针的「读出全部属性清单」拉出 599 条，按 `VehiclePropertyIds.toString(id)` 搜 `FUEL` / `GEAR` / `RANGE`；
2. 或直接在 `CarLampSource` 加两个只读方法（`getFloatProperty(0x11600309, 0)`、`getIntProperty(0x11400400, 0)`），在 `CarDataMonitor` 日志里打印；
3. 结果三选一：有值 → 升级为 A 级；`available=false` → 归 C 级；抛异常 → 记录后归 C 级。

### 2.4 当前拿不到（C 级，明确不做）

| 数据 | 说明 |
|---|---|
| 道路限速 / 限速牌 | 0x5201/0x5202 解码里没有 speed limit 字段；代码中无任何限速数据 |
| 多车道 / 车道级几何 | 车道事件不稳定，且没有车道级道路模型 |
| 充电 / 电量 | 本车（UNI-V）没有该数据；BYD 专用接口不适用 |
| 挡位 P/R/N/D（当前） | 暂归 C；等 2.3 探针确认后再决定，未确认前停车场景用 `speed = 0` |
| 路况、天气、摄像头 | 无数据源 |

### 2.5 必须先补的前置条件

1. **自定义主题没有启动 `CarDataMonitor`**：目前只有内置双环、NAV_TWIN、bench MCU 层会 `start()`。选中自定义主题时，仪表和任何数据绑定会读到 `NaN`。
   → 需要：主题 attach 时 start、detach 时 stop。
2. **候选属性确认**：油量/挡位按 2.3 的探针跑一次实车；确认前不要写进能力承诺。

## 3. 能力上限（L0–L4）

### L0 静态画面（现在）

图片/渐变/形状/文字/仪表/实时槽位 + 循环关键帧。

### L1 连续数据映射

任何数值 → 任何属性，实时映射（不是关键帧）：

```json
{ "bind": "speed", "map": [0, 220], "to": [0, 1], "property": "ringSweep", "clamp": true }
```

可做：速度环、转速光晕/粒子密度、续航条、转向箭头随距离缩放、速度历史曲线（`Info.history` 已有）、颜色随车速渐变。

### L2 事件规则（when → do）

条件支持：阈值、持续 N 秒、边沿、滞回（>120 触发 / <110 复位）、冷却时间、组合（AND/OR/NOT）。

动作支持：显示/隐藏、播放一次性动画、改文字/图片、切状态、切主题、弹横幅、延迟执行。

```json
{
  "when": { "speed": { "gt": 120 }, "for": 3 },
  "do": [
    { "action": "pulse", "layer": "border", "times": 3 },
    { "action": "text", "layer": "hint", "value": "慢一点" }
  ],
  "cooldown": 30
}
```

### L3 场景状态机

状态由数据决定，切换带动画；每个状态有自己的图层可见性/位置/配色。

```json
"states": {
  "idle":    { "layers": { "clock": { "visible": true } } },
  "driving": { "layers": { "speedRing": { "visible": true } } },
  "nav":     { "layers": { "turn": { "visible": true }, "eta": { "visible": true } } },
  "night":   { "palette": "night" }
}
```

### L4 编排与程序化

- 时间线：多轨关键帧、事件点、一次性 intro、切换过渡；
- 序列：滑入→停留→滑出（换歌卡、超速横幅）；
- 程序化原语（参数化，非脚本）：脉冲、闪烁、抖动、扫光、呼吸、速度线、粒子（密度随车速/转速）。

### 能力等级总结

| 等级 | 能力 | 主题的样子 |
|---|---|---|
| L0 | 静态 + 循环动画 | 皮肤 |
| L1 | 连续映射 | 数据驱动的动态仪表 |
| L2 | 事件规则 | 会对数据做反应（提醒/弹卡/闪烁） |
| L3 | 场景状态机 | 停车/行驶/导航/夜间自动换布局 |
| L4 | 编排/程序化 | 开场、过渡、粒子、序列动画 |

做到 **L1 + L2 + L3** 就是“车机表盘引擎”级别；L4 是观感加成。

## 4. 用户能达到的最大效果（完整剧本）

### 剧本 A：运动主题

- 平时：转速光晕随 rpm 变色、速度环随 speed 扫动、速度线随车速加速；
- 高速巡航：100–120 km/h 持续 10 分钟 → 显示“已巡航 10:00”；
- 急加速：1 秒内 +20 km/h → 仪表闪一次橙色；
- 夜间（车灯亮）：暗色配色 + 星点粒子。

### 剧本 B：导航主题

- 导航开始：0.3 秒过渡到导航布局（转向箭头 + 距离 + ETA + 地图）；
- 距离 < 300 m：箭头放大；< 50 m：闪烁；
- 环岛：显示“第 N 出口”并高亮；
- ETA 变晚：`+N 分` 闪红 3 秒；
- 剩余 < 1 km：显示“即将到达”；
- 导航结束：回到行驶布局。

### 剧本 C：信息与休息主题

- 停车（speed = 0 持续 5 秒）：大时钟 + 日期 + 总里程；
- 连续行驶 2 小时：提示“该休息了”，每小时一次；
- 换歌：歌名卡片从右侧滑入，停留 5 秒滑出；
- 低续航：range < 80 km 图标呼吸，< 50 km 红色闪烁；
- 补能检测：range 突然增加 → 播放一次“补能”动画（不依赖充电信号）。

### 剧本 D：数据驱动的背景

- 粒子/速度线密度与车速、转速挂钩；
- 夜间星空/流星；
- 主题载入 1.5 秒开场（扫光 + logo 浮现 + 仪表扫满）。

**最大效果一句话：主题会看数据、会做反应、会换场景、有开场和过渡——接近成品车机主题引擎，但仍然是可校验的声明式 JSON，没有脚本、没有网络。**

## 5. 明确做不到的

- 按**道路限速**变色/报警（无限速数据）；
- 限速牌识别；
- 按车道选路/车道级提示（车道数据不稳定）；
- 充电、电量场景（本车无数据）；
- 挡位场景（当前无接口，探针确认后再定；未确认前用停车代替）；
- 路况/天气/摄像头触发；
- 任意逻辑、循环、函数、网络、视频、3D。

## 7. 兼容性

- 全部按“新增可选字段”实现：无 `rules/states/bind` 的主题行为与今天完全一致；
- 旧 App 读到新字段会忽略，渲染基础层（静态可看）；
- 红线：不改 `dst` 类型、文本绑定用新字段 + 占位回退、调色板在导出时展开、基础层=默认状态；
- 回归基线：`test_theme`、`my_theme`、`red_white_sport` 渲染逐像素对比。

---

## 8. 决策建议

1. **只做两件事**：文本数据绑定 + 事件规则（L1 + L2）。投入最小，主题立刻“活”起来。
2. **追求观感**：再加场景状态机（L3）与时间线（L4）。
3. **先补前置**：自定义主题启动数据监控 + 油量/挡位只读探针——否则数据类能力在真车上不生效。
4. **不做**：限速、多车道、充电/电量，除非未来拿到稳定的数据源；挡位/油量以探针结果为准。

---

## 9. 结论

- 引擎的能力上限：**L1 连续映射 + L2 事件规则 + L3 场景状态机 + L4 编排**。
- 用户的效果上限：**数据驱动的动态仪表 + 场景自动切换 + 事件反应 + 开场/过渡动画**。
- 能力边界由数据决定：A 级数据撑起全部核心玩法；B 级只能做装饰性增强；C 级明确排除。
- 最大前提：先让自定义主题真正拿到车速/转速/续航（补 `CarDataMonitor` 启动），再谈规则和状态机。

## 10. 附：DiPlayThemeMakerWpf 的预览能力评估

问题：**如果上面这些扩展都实现，WPF 制作器能否准确预览？**

结论：**分三层**——静态画面与确定性动画可以做到“准确”；数据驱动行为只能做到“仿真”；实时流与真实媒体只能“占位”。

### 10.1 可以准确预览

- 1920×720 画布、图层 z 顺序、dst 位置/尺寸；
- 图片（fit）、渐变、形状、文字、仪表（speed/rpm）；
- 关键帧动画（alpha/x/y/scale/rotation）与循环时序；
- 底部 110px 安全区标线；
- 主题包内的静态资源和最终构图。

这类内容与设备端共用同一份 theme.json 语义，WPF 与 Android Canvas 的差异主要在抗锯齿/字体度量/阴影，属于像素级微差，布局与比例一致。

### 10.2 需要补“数据模拟器”才能仿真

以下能力依赖运行时数据，预览必须先造数据：

| 能力 | 预览需要的模拟输入 |
|---|---|
| 导航类（转向/距离/路名/环岛/ETA/剩余） | 场景脚本：开始导航 → 距离递减 → 到路口 → 结束 |
| 歌曲类（歌名/歌手/器乐/歌词行/封面） | 手动输入或样例文件；QQ 音乐/Apple Music 两种字段语义 |
| 昼夜/时间 | 时间滑块 + 白天/夜间切换 |
| 续航/里程 | 数值滑块或脚本变化 |
| 音频律动/频谱 | 正弦/噪声模拟或手动 level 滑块 |
| 规则/状态机 | 场景时间线：在 t=3s 把 speed 改到 130，观察是否触发超速规则 |

这些数据 App 端本来就有（车速/转速/导航/歌曲/时间/续航），制作器只要提供“场景时间线”和“数据面板”，就能把规则、状态机、动画触发完整演一遍。

### 10.3 无法准确预览的部分

- **实时流**：`nav` / `card112` 是手机推来的视频流，制作器只能用占位图/模板，无法预测真实画面；
- **真实媒体**：封面分辨率、歌词文本、频谱形状取决于手机与播放器，只能仿真；
- **设备性能**：帧率、掉帧、GPU 差异无法在 WPF 中复现；
- **字体/渲染细节**：WPF 与 Android 的字体度量、阴影、渐变插值存在像素级差异。

### 10.4 保真度的最大风险：双实现漂移

如果规则/状态机在 WPF 用 C# 重写一套，设备端用 Kotlin 一套，两边语义迟早分叉（触发时机、滞回、优先级、冷却）。建议：

1. **单一规格**：rules/states 的 JSON Schema 只有一份，两端都按它实现；
2. **同一组用例**：准备 10–20 个“条件→动作”用例，两端跑同一份数据脚本，比对结果；
3. **golden 截图**：设备截图与 WPF 渲染做像素/结构对比，作为回归基线；
4. **场景时间线**：制作器的预览不是“实时”，而是“按脚本回放”，这样规则行为可复现、可对比。

### 10.5 结论

- 静态布局、图层、仪表、关键帧：**可以准确预览**；
- 数据绑定、规则、状态机、频谱/歌词：**可以仿真预览**，前提是补数据模拟器和场景时间线；
- 实时视频流与真实媒体：**只能占位**，不能承诺“所见即所得”；
- 要做到长期一致，规则引擎必须“一份规格、两端实现、用例对齐”，否则预览会逐渐失真。

## 11. 异形填充与矢量形状扩展（path / polygon）

### 11.1 现状：形状确实很少

| 能力 | 现状 |
|---|---|
| `shape` 类型 | 只有 `rect`、`ellipse` / `circle`；纯填充，无描边、无圆角 |
| 矢量路径 | 没有 `path`、没有 `polygon` |
| 裁剪 / 遮罩 | 没有 `clip`、没有 alpha mask |
| 填充量绑定 | 只有 `gauge` 的弧长跟 speed/rpm；`shape` 不能按数据填充 |
| 异形填充结论 | **连续填充做不到**；只能用「多帧图 + `visibleIf`」做离散分档 |

### 11.2 三层路线

1. **短期（不改代码）**：按 10%–20% 一档做 10–20 张 PNG，每层用 `visibleIf` 的速度/转速区间显示。硬切、图多，但今天就能上。
2. **中期（推荐）**：加**形状库 + `clip` + `fill` 数据绑定**，一次打通“任意形状 + 任意数据 + 连续填充”。
3. **长期（可选）**：形状描边/虚线、按路径运动的粒子、遮罩动画。

### 11.3 建议的形状库

| 形状 | 参数 | 说明 |
|---|---|---|
| `rect` | `cornerRadius` | 现有能力 + 圆角 |
| `ellipse` / `circle` | — | 现有 |
| `ring` | `outerRadius`、`thickness`、`start`、`sweep` | 圆环进度，比 `gauge` 更通用 |
| `arc` | `start`、`sweep`、`thickness`、`cap` | 只描边的圆弧（仪表外框） |
| `polygon` | `points: [[x,y],…]`、`fillRule: nonzero/evenOdd` | 多边形，凹多边形、自交、孔洞都能表达 |
| `path` | `d: "M…L…C…Z"`、`fillRule` | 贝塞尔曲线、圆弧、孔洞；表达力最强 |
| `line` / `polyline` | `points`、`thickness`、`cap` | 装饰线、刻度线 |

所有形状统一支持 `fill`（纯色/渐变）与 `stroke`（颜色、粗细、端点/拐角），并可作为 `clip` 的裁剪源。

### 11.4 path 与 polygon 怎么选

| 维度 | polygon | path |
|---|---|---|
| 表达力 | 直线段、凹形、孔洞（evenOdd） | 曲线、圆弧、任意轮廓 |
| 编辑器 | 拖点即可，最简单 | SVG `d` 文本 + 预览，或钢笔工具 |
| 解析 | 点数组，零风险 | 需路径解析器，要做长度/复杂度上限 |
| 性能 | `clipPath` 后填充矩形，最便宜 | 同 polygon，曲线只是路径段更多 |
| 适合 | 火焰、闪电、折角仪表、油箱 | 有机曲线、复杂外框、精细图标 |

**建议先 polygon 后 path**：polygon 覆盖 80% 的“异形填充”需求，编辑器和校验都简单；path 作为第二期补齐曲线与孔洞。两者共用同一套 `clip` + `fill` 管线，后续加 path 不改已有语义。

坐标约定：
- 默认用 **dst 局部像素**（`0..w, 0..h`），编辑器所见即所得；
- 可选 `"normalized": true` 时用 `0..1`，便于同一形状在不同尺寸/缩放动画下复用；
- 超出 dst 的点在渲染时裁剪，审计脚本报“超出目标区域”。

### 11.5 `fill` + `clip` 数据绑定

```json
{
  "id": "speed_fill",
  "type": "polygon",
  "z": 2,
  "dst": [120, 300, 400, 260],
  "points": [[0,260],[60,220],[120,240],[200,80],[280,200],[340,150],[400,180],[400,260]],
  "fillRule": "nonzero",
  "bind": { "source": "speed", "range": [0, 220], "direction": "up", "ease": 12 },
  "paint": { "kind": "linear", "colors": ["#00E5FF", "#0044FF"], "from": [0, 1], "to": [0, 0] },
  "stroke": { "color": "#7FE7FF", "width": 2 }
}
```

```json
{
  "id": "rpm_path_fill",
  "type": "path",
  "z": 2,
  "dst": [900, 200, 300, 300],
  "d": "M150,10 C220,10 290,80 290,150 C290,230 220,290 150,290 C70,290 10,230 10,150 C10,80 80,10 150,10 Z",
  "normalized": false,
  "bind": { "source": "rpm", "range": [0, 8000], "direction": "radial", "ease": 10 },
  "paint": { "kind": "radial", "colors": ["#FFD166", "#FF6B35"], "center": [0.5, 0.5], "radius": 0.6 }
}
```

实现要点：
- 先用形状构建 `Path`，`canvas.clipPath(path)`，再按 `fill` 比例画填充矩形/圆/扇形；
- `direction`：`up/down/left/right`（矩形推进）、`radial`（同心扩散）、`sweep`（绕中心扫角）；
- `ease`：对 150 ms 的车辆数据做低通，避免阶梯跳变；
- 软边用 alpha 遮罩（`saveLayer + DST_IN`），代价高于 `clipPath`，只建议 1–2 层用；
- 形状同时可作为其他图层的 `clip`，例如把一段渐变/扫光裁进异形区域。

### 11.6 编辑器与预览

- WPF：polygon 用画布拖点编辑；path 用文本框输入 `d` + 实时预览（WPF 的 `Geometry.Parse` 可直接解析同语法子集）；
- 填充预览：速度/转速滑块直接驱动 `fill`；
- 遮罩：从主题目录选 PNG，预览用 `OpacityMask`；
- 审计：`theme_audit.py` 增加“点越界、路径过长、层数过多”告警。

### 11.7 成本与兼容

| 项 | 规模 | 风险 |
|---|---|---|
| polygon 形状 + 填充/描边 | 1 天 | 低 |
| `clip`（path/polygon） | 1 天 | 低，`clipPath` 硬件加速 |
| `fill` 绑定 + 方向 + ease | 1 天 | 低 |
| path 解析（SVG 子集） | 1–2 天 | 中，要做复杂度/长度上限 |
| alpha 软边遮罩 | 1 天 | 中，老 GPU 的 `saveLayer` 开销 |
| WPF 编辑器（polygon/path/填充滑块） | 3–5 天 | 中 |
| 兼容性 | 纯新增字段；旧 App 对未知类型不绘制，旧主题零变化 | 低 |

### 11.8 结论

- 现在：**没有 path/polygon/clip，形状只有矩形和椭圆**，连续异形填充做不到；短期只能用多帧 + `visibleIf` 近似。
- 扩展后：**polygon 先上、path 后上**，配合 `clip` + `fill` 绑定，就能做到“任意形状 + 车速/转速连续填充 + 渐变/描边”，成本可控且完全兼容旧主题。

**落地状态**：polygon schema 已定稿（见 `CUSTOM_THEMES_VECTOR.md`）；审计规则已写入 `tools/theme_audit.py`（vector 图层结构校验 + “当前尚未渲染”提示）。path 作为下一期，schema 预留 `shape:"path"`。

### 12.2 P0（2026-11-12 实车确认）：数据启动权不在主题——内置主题能动，自定义主题不动

> 修订记录：初版判定“三个数据能力全部失效”；当天根据口述“真车 release 也有效果”弱化成“不一定失效”；
> 随后车机实测：**内置主题的仪表弧随车速/转速变化，导入的自定义主题不动**——初版结论成立，弱化撤回。
> 保留“为什么 PC 上一切正常”的解释，这是最容易误导人的地方。

**现场记录（2026-11-12，车机）**

| 场景 | 仪表弧 | 说明 |
|---|---|---|
| 内置主题（双环等） | 随车速/转速变化 | `PortholeDualRingView.start()` 启动了监控 |
| 导入的自定义主题（车机） | 不动 | 没有任何视图启动监控，`NaN` 兜底成 0 |
| WPF 制作器 | 正常 | PC 端自己模拟 speed/rpm，不读车机数据 |
| 手机/叠加副屏 + bench | 正常 | `BenchMcuView` 启动监控 + `BENCH_VEHICLE` 注入 speed/rpm |

机制（逐行可查）：

1. `CustomThemeHost.attach()` 只创建 View、起 33 ms ticker；`detach()` 也不 stop；
2. 全仓库 `CarDataMonitor.start` 只有 4 处：`PortholeDualRingView.start()`、`PortholeNavTwinView.start()`、
   `BenchMcuView`（可见时）、`BenchClusterReceiver`（一次性探针）；
3. 切到自定义主题时，双环和导航双擎都会被 `clearPortholeThemeForSwitch()` / `applyPortholeTheme()` 的自定义分支 stop 掉；
4. 剩下唯一可能启动它的是 `BenchMcuView`，它只在 `BenchCluster.enabled || simulatedOverlayDisplay` 时创建，
   而 `simulatedOverlayDisplay` 的定义是**副屏名字含 `叠加` 或 `overlay`**（`ClusterMapPresentation.kt` 约 170 行）。
   本次测试的车机不是这种副屏，所以没有任何视图替主题启动监控——这正好解释了“内置动、自定义不动”。

**为什么两条预览路径都发现不了**：WPF 制作器是**自己模拟** speed/rpm，压根不读设备数据；手机/PC 的“叠加视图”副屏则是
`simulatedOverlayDisplay=true` → `BenchMcuView` 常驻并启动监控，再用 `BENCH_VEHICLE` 注入 bench 值。
两条路都绕开了“真车上没人启动监控”这个事实，所以预览永远是对的、车机永远是 0。

失效表现（自定义主题、无 bench 时）：

| 能力 | 读数据位置 | 实际表现 |
|---|---|---|
| `gauge` | `CustomThemeLayerView.drawGauge()` | `NaN` → 0，弧长恒为 0（已实车确认） |
| `visibleIf` | `CustomCondition.matches()` | `NaN` 当 0：`speed.gte:0` 恒真、`speed.gte:10` 恒假、`lte:0` 恒真 |
| `swap`（动态图） | `swapMatches()` | 只有下限 ≤0（且上限 ≥0）的分支会命中，等于静态图 |
| 将来的 `bind` | — | 同样读到 `NaN` |

为什么不容易当场发现：停车时真实车速/转速本来就是 0，`NaN` 兜底也是 0，**静止状态两者完全一样**，
只有开起来才分得清；再加上 PC 预览一直正常，很容易把“主题能显示”当成“数据通了”。

修法（阶段 0，0.5 天）：`attach()` 里 `CarDataMonitor.start(context)`，`detach()` 里 `stop()`。
该对象已有引用计数，和内置主题共存不会互相打断；同时把“数据启动”写进主题的职责，不再依赖副作用。

**复核命令**（换车/换副屏时用）：

```bash
adb shell dumpsys display | findstr "叠加 overlay"
adb logcat -s CarDataMonitor DiPlay-CustomTheme
```

切成自定义主题后 10 秒内：

- 没有 `car data monitor start` → 数据没在跑（本次车机就是这个状态）；
- 有 start 且每 5 秒一条 `car data speedRaw=...` → 在跑，大概率是 `BenchMcuView` 的功劳。

> 附：手机/平板测试机没有 `android.car`，`BENCH_DATA` 探针会返回
> `ClassNotFoundException: Didn't find class "android.car.Car"`（2026-11-12 实测）。
> 这类设备只能靠 bench 注入值，**不能用它判断主题在车上是否正确**。

### 12.3 复核后的能力基线（覆盖 §1）

| 能力 | §1 初评说法 | 代码事实（2026-11-12） |
|---|---|---|
| 图层类型 | image/brush/shape/text/gauge/live | 一致；另有 `swap`（图片换帧）未写进 §1 |
| 形状 | `rect` / `ellipse` | 一致；纯填充，无描边、无圆角、无 path/polygon |
| 文本 | 单行左对齐 | 一致：`drawText` 于 `dst.left, dst.top+fontSize`，无换行、无 align、无数据绑定 |
| 动画 | alpha/x/y/scale/rotation，可循环 | 一致；`loop:false` 也有实现，live 视图同样吃关键帧（11-11 修复） |
| 条件 | 车速/转速区间 + appleFullMap | 一致；无夜间、无续航、无导航、无持续时间/边沿 |
| 数据 | 仅仪表能用 speed/rpm | 读数路径都在，但没有任何视图替自定义主题启动监控——2026-11-12 实车：内置动、自定义不动 |
| `z` | 建议 0–150 | 实际 `coerceIn(0, 1900)`；主题切换遮罩是 2500，主题层压不过它 |
| 性能 | 未评估 | 每层一个**全屏**透明 View，33 ms 对**所有层无条件 `invalidate()`**，且每 tick 走一次 `reorderThemeLayers()` |
| vector | 未渲染 | `type` 能读进来，但 `points`/`fillRule`/`paint` 等字段没解析，`when(type)` 也没有分支 → 整层不绘制 |
| bind/rules/states | 无 | 一致：schema 里零字段 |

补充一条容易被忽略的约束：`visibleIf`、`swap`、`gauge` 都是**每帧求值**（30 fps），不是事件式；这决定了后续做“持续 N 秒/边沿/冷却”时必须新增状态，而不能沿用现在的写法。

### 12.4 先定三个设计决策（不定就会返工）

**D1｜数据快照 `ThemeData`：一次采集，全员共享，可注入**

现在是每个图层各自去 `CarDataMonitor` 读一遍。要加文本绑定、条件扩展、规则、状态机，必须收敛成一个不可变快照：

```
ThemeData(speedKmh, rpm, odometerKm, rangeKm, night, appleFullMap,
          wallClock, themeClock, nav{remainingKm, remainingMin, arrivalClock, deltaText, subtitle},
          song{title, artist, key})
```

由 Host 每 tick 采一次，`CustomThemeLayerView.setData(data)` 下发。收益有三：
① 每帧只读一次；② Robolectric 单测可以直接喂值，不依赖车机；③ PC 预览与车机可以喂同一份脚本，减少双实现漂移。

**D2｜属性所有权与优先级（现在没写，做 bind 前必须写死）**

建议按“越晚、越具体，优先级越高”排：

```
静态 dst/alpha/scale/color  <  关键帧动画（叠加：+ 或 ×）  <  bind（改基础值）  <  rule 动作（有 TTL，过期归还）
```

这样能和现有语义无缝共存：`x = rect.left + keyframe("x")`、`alpha = baseAlpha × keyframe("alpha")` 都不变，`bind` 只是换掉 `rect`/`baseAlpha`/`baseScale`，规则动作用短暂覆盖层实现。**不写死这条，规则和关键帧一定会互相打架。**

**D3｜兼容红线（沿用 §7，并补三条）**

1. `text` 永远是**静态兜底**，模板放新字段 `bind.template`——旧 App 打开新主题显示的是可读的占位文字，不是 `{speed:0}`；
2. 所有新能力都是“可选字段 + 缺省等于今天行为”，旧主题必须零变化；
3. 未知 `type` 不绘制（vector 已天然满足），未知字段忽略；`schema` 仍为 1。

#### 阶段 1：数据能显示（文本绑定 + 条件扩展，L1a）

- **目标**：主题上出现**真实数字与文字**，并让显隐条件覆盖全部 A 级数据。
- **做什么**
  1. `text` 图层新增 `bind`：

     ```json
     { "id": "speed_num", "type": "text", "dst": [120, 300, 420, 120], "fontSize": 96,

       "bind": { "template": "{speed:0} km/h", "fallback": "--", "throttleMs": 200 } }
     ```

     规则：有 `bind` 时画 `template`，`{source:精度}` 展开；无值（`NaN`/未连接）画 `fallback`；没有 `bind` 时行为与今天完全一致。`text` 作为旧 App 的静态兜底。

  6. `theme_audit.py` 增加 `bind` 字段校验；`CUSTOM_THEMES.md` 补第 4.4 节与条件表。
- **规模**：M，2–3 人日。
- **退出标准**：一个 demo 主题同时显示 实时车速 / 续航 / 导航剩余 / 歌名，夜间自动换文字色，低续航（`range < 50`）出现提示层；无数据时显示 `fallback` 而不是 0；旧 APK 打开显示静态 `text`；数字肉眼不抖。
- **不做**：数值驱动颜色/位置（阶段 2）、事件规则。
- **落地状态（2026-11-12）**：App 侧 + WPF 侧完成——`ThemeData` 快照、`text.bind`（template/fallback/throttle）、

#### 阶段 2：数据能驱动外观（连续映射，L1b）

- **目标**：数值 → 任意外观属性，连续、带缓动；这是后面 vector 填充和规则动作的共同底座。
- **做什么**
  1. 图层级 `bind`（与阶段 1 同名但语义是“映射”）：

     ```json
     "bind": { "source": "speed", "from": [0, 220], "to": [0.4, 1.0], "clamp": true, "ease": 120 }
     ```

     作用对象按顺序补齐：`alpha` → `scale` → `rotation` → `x/y` → `color`（`from/to` 两色插值）。
  2. 每层维护低通状态 `level += (target-level)*(1-exp(-dt/ease))`（`CUSTOM_THEMES_VECTOR.md` 已给公式，这里落地为公共实现）。
  3. 按 D2 实现优先级：`bind` 改基础值，关键帧仍在其上叠加。
  4. WPF：`PreviewControl` 每 tick 用现有滑块值重算属性即可，成本很低。
  5. 审计 + 规范补 `bind` 的两种用法（文本 vs 属性）说明，避免作者混淆。
- **规模**：M，2–3 人日。
- **退出标准**：速度→颜色、速度→缩放、转速→透明度、续航→位移四个 demo；车机 ≥30 fps 不掉帧；旧主题逐像素一致。
- **落地状态（2026-11-12）**：App + WPF 完成——`CustomBindSpec` / `ThemeBind`、图层 `bind`（alpha/scale/rotation/x/y/color）、
  `ease` 低通、D2 叠加（bind 改基础值，关键帧仍在其上）；WPF 读写、`--selftest` 往返、`--preview-shot` 注入；
  审计与规范 §4.4.2；示例 `custom-theme-test/bind_demo` 覆盖四个退出标准映射。
  模拟器通过（WPF 0/220 km/h、0/7000 rpm、100/400 km 截图；手机挂载 8 图层无崩溃）。
  **WPF 编辑面板已提供属性绑定、常用示例、当前映射说明和即时校验；`--editor-shot` / `--editor-apply` 自检通过；
  车机帧率与观感待验。**
- **不做**：vector（下一阶段）、规则。

> 说明：`gauge` 今天已经能按 speed/rpm 画弧，所以阶段 2 不是“从零做仪表”，而是把“映射”从仪表里抽出来，变成任意图层可用。

#### 阶段 3：异形与描边（vector polygon）

- **目标**：补齐 §11 的落地：任意多边形 + 纯色/渐变填充 + 描边 + 数据填充。
- **做什么**
  1. `CustomThemeSpec.parseLayer` 认识 `type:"vector"`、`shape:"polygon"`；

  3. `bind` 的 6 个 `direction`（up/down/left/right/radial/sweep）+ `ease` 直接复用阶段 2 的插值器；
  4. 审计把“当前尚未渲染”提示改成已支持；`CUSTOM_THEMES_VECTOR.md` 升 v1.0；
  5. WPF：polygon 画布拖点编辑 + `Geometry.Parse` 预览 + 填充滑块。
- **规模**：M–L，4–6 人日（App 2–3 + WPF 2–3）。
- **退出标准**：规范 §6.1（车速灌满异形）与 §6.2（转速中心扩散）在车机上正确；点越界被裁剪；描边不被裁掉；旧 App 打开不画 vector（无错误色块）。
- **落地状态（2026-11-12）**：App + WPF 完成——`CustomThemeSpec` 解析 polygon/points/normalized/fillRule/stroke/fill bind；
  `drawVector()` 用 clipPath 画六方向填充并在 restore 后描边；WPF `VectorVisual` 同语义、支持 linear/radial/sweep（sweep 用扇形近似）；
  审计、`CUSTOM_THEMES.md`/`CUSTOM_THEMES_VECTOR.md`、示例 `custom-theme-test/vector_demo`；
  WPF 编辑器支持 points/归一化/fillRule/纯色/渐变/描边/填充绑定与实时预览，`--editor-apply` 往返通过。
  模拟器通过（WPF 低/高两档截图；手机挂载 7 个图层无崩溃）。**拖点编辑、path、clip、虚线未做；车机待验。**

- **不做**：`path` 曲线、`clip` 引用、虚线描边。

#### 阶段 4：事件规则（L2）

- **目标**：条件 → 动作；主题开始“有反应”。
- **做什么**
  1. `rules` 数组 + 条件求值器：阈值、持续 N 秒、边沿、滞回（>120 触发 / <110 复位）、冷却、AND/OR/NOT；
  2. 动作：`show/hide`、`pulse`、`setText`、`setImage`、`flash`、`switchState`、`delay`；动作带 TTL，结束后按 D2 归还属性；
  3. 用单调时钟（`SystemClock.elapsedRealtime`）；规则状态随 Host attach/detach 重置；
  4. WPF：**第一次真正需要数据模拟器**——场景时间线（t=3 s 把 speed 改到 130），否则规则无法在制作器里验证；
  5. 建 10–20 条“条件→动作”用例表，两端跑同一份脚本比对。
- **规模**：L，5–7 人日（引擎 3–4 + WPF 时间线 2）。
- **退出标准**：超速（>120 持续 3 s，冷却 30 s）与急加速（1 s 内 +20 km/h）两个用例在车机与 WPF 结果一致；连续 10 分钟无重复触发、无抖动。
- **落地状态（2026-11-12，v4 切片）**：App + WPF 已完成单条件或一层 AND/OR/NOT（最多 3 个叶子）、`speedDelta` 急加速、
  `pulse`/`setText`/`setImage`、`durationMs` 动作 TTL、WPF 场景时间线；WPF 规则窗口用“单条件/全部满足/任一满足 + 取反 + 附加条件行”编辑。
  `CustomRuleEngineTest` 11 条引擎/解析用例；手机 0→25 km/h 急加速、130 km/h 超速、夜间+110 AND；setImage 在 WPF 130/100 截图验证。
  **未做**：条件嵌套超过一层、`switchState`/`delay`、10 分钟稳定性与车机待验。
- **不做**：状态机（下一阶段）、条件嵌套过深（限制一层组合）、任何脚本能力。

### 12.7 为什么是这个顺序

```
阶段0 ──┬── 阶段1 ── 阶段2 ── 阶段3
        │                └──── 阶段4 ── 阶段5 ── 阶段6
        └── 探针（并行，不阻塞）
```

- **阶段 0 第一**：数据启动权现在挂在别的视图上，能不能用取决于副屏名字和前置主题（§12.2），
  不先收回这个权力，后面所有数据能力都无法稳定验证；
- **阶段 1 第二**：schema 改动最小、用户感知最强，还能顺带验证 D1（快照）和 D3（兼容红线）；
- **阶段 2 第三**：把“映射”从仪表里抽成公共能力，成本低，但它是阶段 3 填充与阶段 4 动作的共同底座；
- **阶段 3 在规则之前**：风险低、schema 和审计已就绪、不引入运行时状态；而规则一旦上马就需要“有东西可动”（bind 目标）和“显示可信”（文本）；
- **阶段 4 → 5**：同一套条件求值器的递进，拆开做比合起来做可控；
- **阶段 6 最后**：收益最低，且最容易把性能预算吃穿。

**如果只能做一件事**：做阶段 1（前提是阶段 0）。一个“实时数字 + 夜间配色 + 低续航提示”的主题，已经足够让人相信这套引擎活了。

**对初评 §8 的修订**：初评说“只做两件事：文本绑定 + 规则”。复评结论是顺序要改——规则不该排第二，因为它价值依赖阶段 2/3 的可动目标和阶段 1 的可信数据；而 vector 应从“中期”提到规则之前。

### 12.8 每阶段的完成定义（DoD）

一个阶段只有同时满足下面 6 条才算完成，缺一条都会在下一阶段返工：

1. **规范**：`CUSTOM_THEMES.md` / `CUSTOM_THEMES_VECTOR.md` 同步更新字段与示例；
2. **审计**：`tools/theme_audit.py` 能校验新字段，缺省/非法值有明确提示；
3. **制作器**：WPF 能读、能存、能编辑、能预览；每个新字段必须有输入控件（不能编辑的新字段等于没有），
   并用 `--editor-apply` 回归确认保存不丢字段；
4. **用例表**：每条新能力配 1–2 条 JSON 用例 + 期望结果，WPF 与车机跑同一份；
5. **回归**：`test_theme` / `my_theme` / `red_white_sport` 渲染逐像素对比无差异（新增能力除外）；
6. **实车**：至少一次车机验证 + 日志留存（含数据值、帧率、stop/start）。

### 12.9 现在就能开始的 3 件事

1. **阶段 0：把数据启动权收回主题宿主**（0.5 天）：`attach/detach` 成对启停监控 + `ThemeData` 快照；先让车机上的仪表动起来（已实车确认当前不动）；
2. **油量/挡位只读探针**（并行，一次实车）：按 §2.3 的方法跑，结果决定它们进 A 级还是 C 级；不要阻塞阶段 1；
3. **`ThemeTextFormat` 纯函数 + 单测**（半天，无 UI 依赖）：精度、单位、`NaN` 回退、节流；这是阶段 1 里最容易写错、也最容易先写对的部分。

### 12.10 风险与止损

| 风险 | 具体表现 | 止损 |
|---|---|---|
| 性能 | 每层全屏 View + 33 ms 全量 `invalidate` + 每 tick 重排；层数一多就掉帧 | 阶段 2 前先测车机帧率基线；审计加“层数 ≤12”告警；vector 支持多形状容器；必要时只 invalidate 有变化的层 |
| 双实现漂移 | WPF 与 Android 对规则/映射语义分叉 | 一份 schema + 用例表 + golden 截图（§10.4 已给方法） |
| 数据抖动 | 150 ms 采样 + 30 fps 渲染，数字跳、仪表抖 | 节流 + 低通（`ease`），文案去抖单独一套 |
| 规则抖动 | 阈值附近反复触发/动作叠加 | 边沿 + 滞回 + 冷却 + 单调时钟；动作幂等、可撤销 |
| 数据不稳 | 车道/连接态等 B 级数据时有时无 | 只允许做装饰，不得作为核心布局的唯一条件（沿用 §2.2） |
| 编辑器黑洞 | rules/states 的可视化编辑器无底洞 | 只做“表单 + 时间线”，不做节点图编辑器 |

### 12.11 复评结论（替换 §0 的一句话结论）

主题引擎的**能力上限**不变：L1 连续映射 + L2 事件规则 + L3 状态机 + L4 编排。
但**当前落地状态**比初评更靠前也更靠后：靠前在于 `swap`、live 关键帧、动画在真车上确实是活的；
靠后在于**数据链路没有任何启动者**——2026-11-12 车机实测：内置主题弧随车速/转速变化，导入的自定义主题不动（§12.2）。
所以准确的说法是：**渲染/动画/live 一直正常，数据部分在车机上等于静态**；这不是“碰运气”，而是当前路径上确实没有 `start`。

所以路线只有一句：**先把数据接通（阶段 0），再让数据能被看见（阶段 1），再让数据能改变外观（阶段 2），然后才是异形（阶段 3）、规则（阶段 4）、状态机（阶段 5）、编排（阶段 6）。**
