# 自定义主题「插件化」可行性评估

**评估对象**：DiPlay 取景窗「自定义主题」能否采用 C# 式插件模型——App 固定扫描目录、加载 DLL、检查接口、传入 Surface / View / 对象并运行。

**日期**：2026-11-14  
**性质**：技术评估与决策参考，**不含实现**。本轮未修改任何代码，未改 `versionCode` / `versionName`。  
**依据**：`CustomThemeSpec.kt`、`CustomThemeHost.kt`、`CustomThemeLayerView.kt`、`ClusterMapPresentation.kt`、`mobile/build.gradle.kts`、`CUSTOM_THEMES.md`、`自定义主题扩展能力评估.md`。

---

## 0. 结论（先看这一节）

1. **机制上可行。** Android 的“DLL”等价物是 **dex / jar / apk**，用 `DexClassLoader`（或 `InMemoryDexClassLoader`）加载，反射拿类，`isAssignableFrom` 检查接口，然后直接调用接口方法。你描述的“C# 扫描目录 → 加载 → 找接口 → 传对象 → 运行”在 Android 上有一一对应，而且能在 Android 9 车机上跑通。

2. **但它不是“C# 那样”的等价物。** C# 有 AppDomain / 可卸载的 `AssemblyLoadContext`、自动依赖探测、XAML/资源、AnyCPU、成熟的插件生态；Android 没有确定性卸载、没有自动依赖探测、raw dex 没有资源、native 按 ABI、release 默认 R8 混淆。照搬会踩一串坑。

3. **对 DiPlay 的自定义主题，不建议现在做 DEX 插件。** 原因不是“加载不了”，而是：
   - **安全**：插件以宿主 UID 运行，能读 CarPlay 身份凭证、车机数据、root；主题是分享/下载的，等于远程代码执行。
   - **稳定**：同进程崩溃 / ANR / OOM 会带走整个仪表；车机黑屏是安全问题。
   - **工具链**：主题作者要 Android SDK / Gradle / D8，WPF 制作器无法预览，静态审计失效——这三样正是你们现在的核心工作流。
   - **收益**：现有 JSON 引擎已经覆盖 L1–L4（绑定 / 规则 / 状态 / 开场 / 序列 / 矢量 / 频谱 / 直播槽位），插件能补的主要是“任意 Android UI / 第三方库 / GL / 视频 / 网络”，这些恰恰是车机主题最不该开放的部分。

4. **如果一定要做**：做“**插件图层**”，不要做“**插件主题**”——保留 `theme.json` 的布局 / 数据 / 规则，只让插件在某个 `dst` 矩形里画自定义内容；插件 API 只给 `Canvas + ThemeData + 只读资源`，不给 `Surface` / `View` / `Context` 的完整控制权。这样风险、API 面、工具链冲击都会小一个量级。

**一句话**：Android 可以做到 C# 式插件；但“主题目录里的 dex”是一个代码分发/安全产品，不是主题格式的升级。

> **2026-11-14 补充（目标澄清）**：本节针对“通用、可分享的主题目录 dex 插件”。如果目标是复刻内置“火焰双擎”这类效果，见 **§11**：可信的 **Canvas 自定义主题运行时** 是可行的，而且比通用 DEX 插件更聚焦；仍然不建议把未签名 dex 放进可分享主题目录。

## 1. 你的设想逐条对照 Android

| 设想（C#） | Android 对应 | 可行性 | 关键点 |
|---|---|---|---|
| 固定目录扫 `*.dll` | `File.listFiles` 扫 `*.jar` / `*.apk` / `*.dex` | 可以 | 目录必须在 App 私有空间；不要把代码和可分享的 `theme.json` 放同一目录 |
| `Assembly.LoadFrom` | `DexClassLoader(dexPath, codeCache, null, parent)` | 可以 | 普通 `javac` 出来的 jar 不能直接加载，必须 D8 成 dex；`minSdk` 决定 dex 版本 |
| `typeof(IPlugin).IsAssignableFrom(t)` | `ThemePlugin::class.java.isAssignableFrom(cls)` | 可以 | 插件不能自带接口类的副本，否则两个 classloader 的接口不是同一个类 |
| 传 `Surface` / `View` / 对象 | 同进程直接传 Java 对象 | 可以 | `Surface` 单生产者；`View` 只能同进程；对象必须是稳定 API 类型 |
| `plugin.Run(host)` | 接口回调 `attach / onFrame / detach` | 可以 | 生命周期、线程、异常、资源释放都得宿主管；没有 AppDomain 隔离 |

最小形态（示意，不是落地代码）：

```kotlin
val loader = DexClassLoader(dexPath, context.codeCacheDir.path, null, context.classLoader)
val cls = loader.loadClass(entryClass)
require(ThemePlugin::class.java.isAssignableFrom(cls)) { "not a theme plugin" }
val plugin = cls.getDeclaredConstructor().newInstance() as ThemePlugin
plugin.attach(host)
```

这段能跑，但它只是“能跑”；下面才是成本。

## 2. 和 C# 的本质差异

| 维度 | C# | Android | 影响 |
|---|---|---|---|
| 运行时 | .NET IL / JIT | DEX / ART | 插件必须 D8/R8，不能直接扔 `csc` 产物 |
| 隔离与卸载 | AppDomain（.NET Framework）、collectible ALC（.NET Core） | classloader 无确定性卸载；`DexClassLoader` 无 `close()` | 更新插件 = 重启 App；反复加载会泄漏 classloader / 类元数据 |
| 依赖 | 自动从同目录 / ALC 探测 | 只加载 `dexPath` 里的 dex；依赖要打包进去 | 第三方库、Kotlin stdlib、AndroidX 都要处理冲突 |
| 资源 | embedded resource / satellite assembly / XAML | raw dex 没有 `resources.arsc`；XML 布局 / `R` 不可用 | 插件只能用 Canvas 画，或走 APK / `addAssetPath` 隐藏 API |
| native | P/Invoke 任意 DLL | JNI `.so` 按 ABI；linker 命名空间 / 可执行权限限制 | 不要做 native 插件；Android 15 还有 16KB 页对齐 |
| 签名 | Strong Name（可选，不等于安全） | APK 签名（安装时）；raw dex 没有签名 | 自己实现签名 / 哈希校验，否则谁都能换代码 |
| 混淆 | 可选 | release 默认 R8 | API 必须 `-keep`，否则 debug 能跑、release `NoSuchMethodError` |
| 工具链 | Visual Studio / `dotnet build` | Android Studio / Gradle / D8 / SDK | 主题作者门槛从“写 JSON”变成“会 Android 开发” |
| 崩溃隔离 | 进程内异常可捕获；AppDomain 可卸载 | 同进程崩溃 / ANR / OOM 带走宿主；无轻量沙箱 | 车机仪表黑屏，属于安全问题 |

三个最容易低估的点：

1. **类身份**：`isAssignableFrom` 比较的是“由哪个 classloader 加载的类”。插件如果把 API 一起打进去，即使包名类名一模一样，也会返回 false；或者更糟，`ClassCastException`。API 必须 `compileOnly`，宿主 parent-first。
2. **R8**：release 会把宿主 API 改名 / 裁剪。插件按原始名字编译，release 里就找不到。必须给 API 加 keep 规则，并且**用 release 包实测**，不能只测 debug。
3. **资源**：raw dex 里没有 `R.layout` / `R.drawable`。想让插件用 XML 布局、AndroidX 控件、Compose，基本要把它做成已安装 APK 或反射 `AssetManager.addAssetPath`；前者不是“扫目录”，后者是隐藏 API，Android 9 能用、未来不保证。

## 3. 技术可行性分级

### 3.1 能做（有成熟先例）

- 扫目录、读 manifest、按需加载 dex；
- 接口 + 工厂 + 生命周期回调；
- 同进程传 `Surface`、`View`、POJO；
- 用 `Canvas` 画自定义内容；
- 插件用自己的 `TextureView` / `SurfaceView` 渲染视频 / GL；
- 用 `PackageManager.getPackageArchiveInfo` 读未安装 APK 的签名 / Manifest（API 28+）。

Android 生态里的 RePlugin、Shadow、VirtualApp、Atlas 都是这个方向；但它们是“插件 APK / Activity 级”框架，比你的需求重得多，且多数已不活跃。你的场景（一个渲染扩展）自己写 loader 更简单。

### 3.2 难做（能做但成本高）

- 插件资源（XML / 图片 / 主题 / 第三方库资源）：要么装 APK，要么隐藏 API；
- 插件里用 Kotlin / AndroidX / Compose：版本冲突、类身份、编译器插件版本；
- 热更新 / 卸载：没有确定性卸载，只能重启进程；
- 崩溃隔离：同进程无法隔离；`:plugin` 进程只能隔离崩溃，不能隔离权限；
- 帧预算 / 超时：主线程回调无法抢占；Surface 独立线程只能“放弃”，不能安全杀线程；
- 多插件依赖冲突：自定义 child-first classloader，复杂且容易出 `LinkageError`。

### 3.3 不该做（对车机主题）

- 从用户可写 / 可分享的目录直接加载未签名 dex；
- 给插件完整 `Context` / `Activity` / `ViewGroup` 根节点；
- 让插件持有 CarPlay 的 nav Surface 或 MCU 层；
- 允许插件启动 Activity / Service、访问网络 / 文件 / root；
- 把“插件加载失败”静默吞掉，或阻塞主题切换；
- 依赖插件自觉释放资源 / 不 ANR。

## 4. 六个硬坑

### 4.1 安全：同 UID + 高价值凭证

插件代码在宿主进程里跑，就是宿主的 UID、宿主的权限。它能：

- 读 `assets/offline-mfi/identity.pk8`、`certificate.p7b`（CarPlay 身份）；
- 读车机数据、日志、配对信息；
- 如果 App 有网络权限，外传；
- 如果车机已 root，调 `su`；
- 篡改主题 / 配置 / 其他插件。

更现实的是**主题分享**：JSON 主题是数据，恶意 JSON 最多画错；dex 主题是代码，下载一个“好看的主题”就等于在车上执行陌生代码。你们现在的主题目录还可能被 `chmod -R 777`（WPF 外置目录推送），这等于把代码注入面进一步放大。

**结论**：插件必须签名（宿主内置公钥 / 哈希白名单），独立 `plugins/` 目录（700），绝不和 `themes/` 混放；发布版只信任开发者签名。社区作者要发插件，就得做密钥管理 / 签名服务——这是一个产品问题，不是技术问题。

### 4.2 稳定：车机黑屏不是普通 crash

同进程插件：

- 抛异常：可以 catch；
- ANR：主线程卡住，系统弹 ANR / 杀进程；
- OOM：整个 App 被杀；
- native crash / `System.exit` / `Runtime.halt`：直接带走进程；
- 死循环：主题切换卡死，仪表一直“正在切换”。

车机仪表黑屏几秒是安全问题。真正的隔离只有：

- **独立 APK + 独立进程 / UID + Service / AIDL**（Android 原生沙箱，但不是扫目录）；
- 或 **`:plugin` 进程 + Surface 跨进程渲染**（同 UID，只隔离崩溃 / 内存，不隔离权限；复杂）。

`:plugin` 进程 + Surface 是“既要插件又要保命”的折中，但 View 不能跨进程，只能用 Surface；输入 / 资源 / 生命周期都要重新设计，工作量约等于一个小型渲染服务。

### 4.3 兼容：R8 / API / dex / 依赖

- **R8**：API 类 / 接口 / 数据类必须 keep；release 实测；mapping 归档。
- **API 版本**：插件 manifest 写 `apiVersion` / `minHost`；宿主不匹配就拒绝，不要 try-catch 硬跑。
- **dex 版本**：D8 按插件 `minSdk` 产出 dex；插件若按 34 编译，Android 9 可能加载不了。要求插件 `minSdk ≤ 28`（车机），最好 25。
- **Kotlin stdlib**：宿主已有 Kotlin；parent-first 会加载宿主的版本。插件用新版 Kotlin 编译可能 `NoSuchMethodError`。要么 Java 写插件，要么锁定 Kotlin 版本。
- **AndroidX / Compose**：同理；Compose 编译器插件版本必须和 runtime 匹配，插件里用 Compose 是高风险。
- **多 dex / 64K**：插件自己可能超方法数；`DexClassLoader` 对多 dex 的支持要验证；主题插件应保持小。
- **Android 14+**：targetSdk ≥ 34 时，动态加载的 dex 必须是只读文件；Android 9 车机不受影响，但代码要向前兼容（复制到内部、设只读，或用 `InMemoryDexClassLoader`）。

### 4.4 渲染：Surface 不是随便传的

- **Surface 单生产者**：CarPlay sink 已经在往 nav Surface 写；插件再往同一个 Surface 画，会抢生产者 / 黑屏。插件只能用**自己的** `TextureView` / `SurfaceView` 的 Surface，或宿主先合成到一块离屏 Surface。
- **View 只能同进程**：跨进程没有 View；跨进程只能传 Surface。
- **SurfaceView vs TextureView**：`SurfaceView` 是独立窗口层，和兄弟 View 的 z-order / 裁剪不好控；`TextureView` 能当普通 View 参与布局 / 变换，但有额外拷贝和延迟。车机 30fps、1920×720，TextureView 通常够用。
- **z-order**：现有主题每层是一个全屏透明 View，live 槽位（nav / 112 / ETA / song）是兄弟 View，MCU 硬件层永远在最上。插件层必须接入这套 z-order，不能自己 `bringToFront` 压过 MCU，也不能遮住 live 槽位（除非主题明确要遮）。
- **帧预算**：33ms/帧；插件 `onDraw` / `onFrame` 超过 8–10ms 就会掉帧；不能在 draw 里分配对象 / 读文件 / 等锁。
- **分辨率 / 密度**：1920×720 是面板像素；插件要按像素画，不要假设 dp；旋转 / 副屏尺寸变化要能重建。

### 4.5 生命周期与热更新

- `DexClassLoader` 加载后不能卸载；换插件版本只能重启 App（或新 classloader，旧的一直泄漏）。
- 主题切换是同步的，还带“正在切换”遮罩；插件加载 / 校验 / 初始化不能卡主线程，必须有超时和失败回退。
- 插件持有 View / Surface / Thread / 静态 Context 都会泄漏；`detach` 必须可靠，但宿主无法强制。
- 没有“插件市场热更新”：每次更新都要重新推包 + 重启；对主题作者迭代很慢。

### 4.6 作者体验与工具链

- 主题作者要装 JDK / Android SDK / Gradle，会写 Kotlin / Java，会配 D8/R8；这不再是“设计师 / JSON 作者”。
- WPF 制作器不能运行 dex；预览只能靠模拟器 / 真机，或者插件作者自己提供截图。
- `theme_audit.py` 只能静态检查 JSON；插件行为无法审计，只能签名 + 人工审核。
- 插件包体积：带 AndroidX / Kotlin 的插件动辄几 MB；WPF 通过 adb 推送、车机存储 / 加载时间都要考虑。
- 兼容矩阵：App 版本 × API 版本 × 插件版本 × Android 版本 × ABI；维护成本会持续增长。

## 5. 放到 DiPlay：现有引擎与插件的冲突

### 5.1 现有能力已经覆盖“主题”该有的绝大部分

`CUSTOM_THEMES.md` 当前能力：image / brush / shape / text / gauge / live / vector / spectrum、swap、text bind、property bind、visibleIf、keyframes、vector 六方向填充、rules（AND/OR/NOT、forMs、回差、冷却、show/hide/flash/pulse/setText/setImage、speedDelta）、states（过渡）、intro、sequence、cover、gif、音频 / 媒体数据。这已经是 L1–L4 的声明式主题引擎。

插件能补的，主要是：

- 任意 Canvas 绘制（path / 粒子 / 自定义 shader 效果）；
- 第三方 View / 地图 / 视频 / WebView；
- 任意 Java / Kotlin 逻辑、网络、文件；
- 复用现有 Android 生态库。

但这些要么可以用“引擎原语”补（path / clip / particles / 表达式），要么是车机主题**不应该**开放的能力（网络 / 文件 / 任意 UI）。真正需要“任意第三方 View”的主题有多少？如果只有 1–2 个，做成内置特效更划算。

### 5.2 与 WPF 制作器 / 审计 / 分发冲突

- 制作器的核心价值是“所见即所得 + 场景时间线 + 静态审计”；dex 插件让这三样都失效或退化。
- 主题分享是社区玩法；插件分享是代码分发，需要签名、审核、版本兼容、崩溃上报——这是另一个产品。
- 你们的发布节奏是“每轮 debug+release、mapping、实车验证”；插件会让每次 App 升级都可能破坏旧插件，测试矩阵翻倍。

### 5.3 车机环境的具体约束

- 车机 Android 9（API 28），1920×720，30fps ticker；
- `targetSdk 37`、`minSdk 25`、release R8；
- 主题目录默认 `/data/data/<pkg>/files/themes`，可改到外部目录；WPF 推送会 `chmod -R 777`；
- 取景窗是 `Presentation` 副屏，主题层是 root FrameLayout 的兄弟 View；live 槽位是 TextureView；MCU 硬件层最上；
- 数据快照 `ThemeData` 每 tick 一次，主题 host 负责启动 / 停止 `CarDataMonitor`。

这些决定了：插件如果要“融入”，只能做**图层**，不能做**窗口 / Activity**；如果要“保命”，只能独立进程 + Surface，不能同进程 View。

## 6. 替代方案对比

| 方案 | 能做什么 | 预览 | 安全 | 性能 | 工作量 | 建议 |
|---|---|---|---|---|---|---|
| JSON 扩展（path/clip/particles/表达式） | 复杂形状、粒子、参数化逻辑 | 完美（WPF 同引擎） | 高（数据） | 高 | 低–中 | **首选** |
| 沙箱脚本（QuickJS/LuaJ） | 任意逻辑：算值、规则、状态、粒子参数 | 好（同一脚本引擎） | 中高（无 I/O，可限内存/指令） | 中高 | 中 | **次选** |
| WebView 主题层（HTML/JS） | 任意 UI/动画/SVG/Canvas | 好（WebView2） | 中（JS 桥/CSP） | 中低（车机 WebView） | 中 | 可选，需实车验证 |
| GLSL / 固定粒子原语 | 火焰/流光/粒子等视觉特效 | 较难（WPF 需 GL） | 中高（无 CPU 代码） | 高（GPU） | 中 | 视觉向可选 |
| DEX 插件（同进程） | 任意 Android 代码/库 | 无 | 低 | 高 | 高 | 仅可信扩展 |
| 独立 APK + Service（跨进程） | 任意代码 + UID 隔离 | 无 | 中（独立 UID） | 中（Binder/Surface） | 很高 | 不推荐做主题 |

**推荐顺序**：JSON 扩展 → 表达式 / 脚本 →（必要时）GLSL / 固定粒子 →（仅可信）DEX 图层 → 不做独立 APK。

### 6.1 为什么“表达式”优先于“脚本”

- 现有 `bind` 只支持线性映射，`rules` 只支持比较；很多“任意逻辑”其实只是算术 / 条件，不需要图灵完备。
- 表达式可以静态校验、WPF 预览、AI 生成、审计；脚本则需要沙箱 / 超时 / 内存限制。
- 先做表达式，能覆盖 80% 的“想要插件”的场景；剩下 20% 再考虑脚本。

### 6.2 为什么“脚本”优先于“DEX”

- 一份 JS / Lua 逻辑，WPF 和 Android 都能跑，制作器可以真预览；
- 不需要 Android SDK / D8 / R8 / 签名 / API 版本；
- 沙箱可控：无文件 / 网络 / 反射，限制内存 / 指令数，超时中断；
- 热更新：重新加载脚本即可，不用重启进程；
- 性能足够：30fps 下做数据 / 规则 / 粒子参数，不做逐像素绘制。

代价：需要引入一个脚本引擎（QuickJS 需 NDK 编 4 个 ABI；LuaJ 纯 Java 更简单但慢一些），以及一套脚本 API / 文档 / 沙箱测试。工期约 1–2 周（不含美术 / 主题）。

### 6.3 WebView 的取舍

- 优点：HTML/CSS/SVG/Canvas 表达力强，WPF 可用 WebView2 预览，作者门槛低，热更新容易。
- 缺点：车机 WebView 版本 / 性能不确定；1920×720 全屏 30fps 可能吃力；透明 WebView 合成成本高；JS 桥是攻击面；和现有 Canvas 引擎是两套渲染。
- 适合：信息卡 / 设置页 / 简单动画；不适合：全屏高频特效 / 和 live 槽位深度混合。
- 必须实车验证后再决定。

## 7. 如果一定要做 DEX：推荐“插件图层”架构

### 7.1 边界

- **不做**“插件主题”（插件接管整个面板 / 生命周期 / 数据）；
- **做**“插件图层”：`theme.json` 里增加一种 layer，引用插件 id + `dst` + `z` + `params`；宿主仍然负责布局、数据、规则、live 槽位、z-order、MCU 顶层。
- 插件只拿到：`Canvas`、`dst`、`ThemeData` 快照、`frameTimeMs`、只读资源读取、日志；拿不到 `Context` / `Activity` / 根 View / `Surface`（v1）。
- 这样即使插件崩了，宿主可以禁用该层、回退到 `fallback` 图片 / 不画，主题其余部分还在。

### 7.2 包格式与目录

```text
files/plugins/
  flame_effect/
    plugin.json          # id, name, version, apiVersion, minHost, entryClass, sha256
    classes.dex          # D8 产物（或 plugin.apk）
    assets/              # 可选，插件自己的图片/数据
    META-INF/SIGNATURE   # ECDSA/RSA 签名，覆盖 manifest+dex+assets
```

- 独立 `plugins/`，权限 700；不要放在 `themes/`，不要 `chmod 777`；
- 宿主启动 / 选中主题时扫描，先读 `plugin.json`，**不要**加载所有类；
- 校验：签名（内置公钥）→ `sha256` → `apiVersion` / `minHost` → 复制 dex 到 `codeCacheDir/plugins/<id>-<hash>/` → 设只读 / 或用 `InMemoryDexClassLoader`；
- 加载：`DexClassLoader(dexPath, codeCache, null, hostClassLoader)`；`loadClass(entryClass)`；`isAssignableFrom`；`newInstance`；
- 缓存：按 `id+version+hash` 缓存 classloader；更新需重启；不要每帧 / 每次切换都新建。

### 7.3 API（Java，版本化）

```java
public interface LayerRenderer {
    void attach(RenderEnv env, JSONObject params);
    void draw(Canvas canvas, RectF dst, ThemeData data, long frameTimeMs);
    void detach();
}

public interface RenderEnv {
    int panelWidth();
    int panelHeight();
    float density();
    InputStream openAsset(String name);   // 插件自己的 assets
    void log(String message);
}
```

- `ThemeData` 是宿主 POJO，插件 `compileOnly`，**不能打包**；
- API 用 Java（避免 Kotlin stdlib / default 参数 / Companion 的耦合）；插件可以用 Kotlin，但需锁定版本；
- `apiVersion=1`，只增不改；删除 / 改签名 = 新 major，宿主拒绝旧插件；
- 所有回调 `try/catch Throwable`；连续 N 次异常 / 单帧超时 → 禁用该插件并回退；
- `draw` 在宿主渲染线程；禁止 I/O / 锁 / 分配大对象；`attach` 里预加载 bitmap；
- 插件不得启动 Activity / Service、不得访问网络 / 文件（API 不提供；但同进程无法强制，靠审核 / 签名）。

### 7.4 渲染模式

| 模式 | 传什么 | 适用 | 风险 |
|---|---|---|---|
| Canvas 回调（推荐 v1） | `Canvas` + `dst` | 2D 特效、粒子、自定义形状 | 插件在主线程画，卡帧影响 UI |
| TextureView 槽位 | `Surface` / `SurfaceTexture` | 视频 / GL / 第三方 View | 生命周期 / z-order / 合成复杂 |
| SurfaceView 槽位 | `Surface` | 全屏背景 / 独立层 | 窗口层，和兄弟 View 混合差 |
| 跨进程 Surface | Binder + `Surface` | 不可信插件 / 崩溃隔离 | 工作量最大；View 不可用 |

v1 只做 Canvas 回调；需要 GL / 视频再评估 TextureView；跨进程最后考虑。

### 7.5 必做测试 / 验收

- release（R8）与 debug 都通过；
- Android 9 实车：主题切换 100 次、30 分钟循环、内存 / classloader 不增长；
- 插件缺失 / 损坏 / 签名错 / API 不匹配 / 死循环 / 抛异常 / 大 bitmap：都能回退，不黑屏；
- 分辨率 / 密度 / 副屏重连 / 旋转；
- 低内存 / 后台 / 进程重启；
- 插件包更新流程（推包 → 重启 → 生效）；
- 文档 / 样例 / CI 模板；
- 安全评审：签名、密钥、目录权限、插件可访问的数据面。

### 7.6 工作量（粗略）

| 阶段 | 内容 | 人日 |
|---|---|---|
| PoC | loader + 接口 + 一个画圆的插件 + 车机跑通 | 3–5 |

## 8. 决策建议

### 现在（0–2 周）

- **不做通用 / 社区 DEX**；如果目标是复刻内置 Canvas 主题，按 §11 的“可信 Canvas 运行时”路线单独验证。
- 补 JSON 引擎的“表达力缺口”：`path` / `clip` / 虚线 / 描边、粒子 / 速度线原语、`bind` 表达式（算术 / 条件）、多段序列。
- 这些能覆盖“插件感”的大部分需求，且保留 WPF 预览 / 审计 / 分享。

### 如果还想要“任意逻辑”（2–4 周）

- 先做**表达式**（安全、可预览、可审计）；
- 再评估 **QuickJS / LuaJ** 沙箱脚本：只算值 / 规则 / 粒子参数，不直接画；WPF 用同一引擎预览；
- 明确脚本 API 白名单：数据只读、无文件 / 网络 / 反射、内存 / 指令 / 时间限制。

### 如果确实需要“任意 Android 绘制 / 第三方库”（1–2 个月）

- 只做**可信插件图层**：签名、独立目录、API keep、Canvas 回调、失败回退；
- 先内部做 1–2 个插件（例如火焰 / 粒子 / 自定义表盘），验证 4 周，再决定是否开放；
- 不要开放给社区下载；不要做“插件主题”；不要从 `themes/` 加载。

### 触发条件（什么时候再考虑 DEX）

1. 表达式 / 脚本 / 原语都表达不了，且；
2. 至少 3 个真实主题需要自定义绘制 / 第三方库，且；
3. 作者是 Android 开发者 / 你自己，且；
4. 你能接受签名审核 + 版本兼容 + 崩溃回退的维护成本。

四条不同时满足，就不做。

## 11. 目标澄清后的补充评估（2026-11-14）：Canvas 自定义主题运行时

> 触发：现有 JSON 做不出内置“火焰双擎”级别的效果。真实目标不是“通用插件”，而是**把内置主题的 Canvas 能力开放给主题作者**：作者拿到画布、数据和事件，自己绘制整屏；同时能设置 111/112 直播流的位置 / 大小 / 缩放，并在进入 / 离开时初始化和清理。

### 11.1 关键事实：内置“复杂效果”就是 Canvas 画的

| 内置主题 / 视图 | 实现 | 关键点 |
|---|---|---|
| 火焰双擎 `PortholeDualRingView` | `View.onDraw(Canvas)` | 36 个火舌 + 140 个火星；`Path` + `LinearGradient` + `RadialGradient`；33ms 一帧；速度 / 转速来自 `CarDataMonitor`；无 GL、无 Surface |
| 导航双擎 `PortholeNavTwinView` | `View.onDraw(Canvas)` | 透明双环层压在 111 全屏导航之上 |
| 射线 `PortholeRayView` / 数学 `PortholeMathView` / 波浪 `PortholeWaveView` / 日夜 `PortholeDayNightView` | `View.onDraw(Canvas)` | 全部是程序化 Canvas |

结论：

1. **Canvas API 足以复刻内置效果**。“JSON 做不到”不是 Android 的限制，是 JSON 表达力的限制；内置主题只是“用 Kotlin 写死的 Canvas 程序”。
2. **但内置主题不是“一个 Canvas”**：火焰背景层、环层、111 导航 TextureView、112 卡片、MCU 硬件层是多层合成。API 必须支持分层 / z-order，不能只给一块画布。
3. 111/112 是**宿主拥有的视频 View**，不能被“画”进 Canvas；只能由宿主按作者给的矩形 / 缩放去摆放，再和作者的 Canvas 层合成。

### 11.2 你的 API 设想：方向对，但还缺三块

你已经想到的：进入接口 + 初始参数 + 事件 + 离开接口 + 让作者设置 111/112 布局。这是对的，而且和内置 View 的 `start/stop`、`setMetrics`、`onDraw` 生命周期同构。

还缺三块：

1. **帧循环**：Canvas 动画需要 `onFrame(canvas, frameState)`，30fps，带 `dt`；只靠事件无法驱动火焰 / 粒子。
2. **分层 / z-order**：主题可能要在导航**后面**画火、在导航**前面**画 HUD；至少需要 background / foreground 两层 Canvas，live 视图夹在中间。
3. **状态 vs 事件**：速度 / 转速 / 频谱是高频状态，放进每帧 `FrameState`；导航开始 / 歌曲切换 / 昼夜 / 档位变化是边缘事件，放进 `onEvent`。全做成事件会风暴，全做成帧状态又会让作者每帧自己 diff。

### 11.3 建议的 API 形态

```kotlin
interface CustomThemeRenderer {
    fun onCreate(host: ThemeHost, params: ThemeParams)
    fun onAttach()
    fun onMetrics(metrics: PanelMetrics)
    fun onFrame(frame: FrameState, canvas: Canvas, layer: CanvasLayer)
    fun onEvent(event: ThemeEvent)
    fun onDetach()
    fun onDestroy()
}
```

- `FrameState`：`timeMs` / `dtMs` / `frameIndex` / `ThemeData` / `cover: Bitmap?` / `spectrum: FloatArray` / `navSlot` / `card112Slot` / `night` / 各字段 `available`。
- `ThemeHost`：`setNavRect(...)`、`setNavTransform(x,y,scale)`、`setNavVisible(...)`、`setCard112Transform(x,y,scale)`、`setCard112Visible(...)`、`loadAsset(name)`、`log(...)`、`requestFrame()`；**v1 不给 `Context` / 根 View / `Surface`**。
- `ThemeEvent`：`NavStarted` / `NavEnded` / `NavUpdated` / `SongChanged` / `PlaybackChanged` / `VehicleData` / `NightChanged` / `Beat` / `VisibilityChanged` / `LowMemory`。
- `CanvasLayer`：`BACKGROUND` / `FOREGROUND`；宿主对每层各调一次 `onFrame`；live 视图在两层之间。
- 线程：`onFrame` / `onEvent` 都在宿主 UI 线程；作者可以开后台线程做物理 / 粒子计算，但不能在后台线程碰 `Canvas`；`onDetach` 必须停线程。
- 生命周期：`onCreate` 一次；`onAttach` 可见；`onDetach` 被切走；`onDestroy` 释放；不可见时宿主停帧；`isActive` token 防止延迟回调。
- 错误：所有回调 `try/catch Throwable`；连续 N 次异常 / 超时 → 禁用该主题并回退到 JSON/内置；日志带主题 id。
- 数据：不可用给 `NaN` / `available=false`，不要伪装成 0（否则 `speed=0` 和“没数据”分不清）。

### 11.5 三个必须定死的设计决策

**D1｜分层与 z-order**

```text
background Canvas  <  nav 111  <  card 112  <  foreground Canvas  <  MCU 硬件层
```

- 作者只能控制自己两层 Canvas 的绘制和可见性，不能 `bringToFront` 压过 MCU；
- 如果主题要“火在导航后面、HUD 在导航前面”，两层够；要更多层说明主题在跟宿主抢布局，不建议；
- 111/112 的可见性、裁剪、圆角由宿主统一处理；v1 不支持作者任意 `clipPath` 视频。

**D2｜事件模型**

- `FrameState` 是唯一事实来源；事件只做“边沿 / 一次性”通知；
- 速度 / 转速不单独发事件（每帧已有），否则 30fps + 150ms 事件重复；
- 事件队列有界、可合并、可丢旧；`onEvent` 不能阻塞生产者；
- 每个事件带 `timestamp` / `sequence`；`onDetach` 后不再投递。

**D3｜直播流布局**

- 111：`setNavTransform(x, y, scale)` 用于每帧动画（便宜）；`setNavRect(l,t,w,h)` 只用于偶发尺寸变化（会触发 relayout / Surface 重建，别每帧调）；
- 112：`setCard112Transform(x, y, scale)`；宽高固定比例，改 width/height 无效；
- 宿主负责 clamp / 安全区 / 缺失（没导航、没 112）时的 fallback；
- 作者拿到 `navSlot/card112Slot` 的当前矩形，用来在 Canvas 上绕开 / 包边。

### 11.6 交付方式：DEX、脚本还是 WebView

| 方式 | 能力 | WPF 预览 | 安全 | 性能 | 适合 |
|---|---|---|---|---|---|
| DEX Canvas 运行时 | 完整 Android / Canvas / 第三方库 | **不能**（Windows 跑不了 dex） | 同 UID，必须签名 / 可信 | 最高 | 你 / 可信 Android 作者 |
| JS / Lua + Canvas binding | 2D Canvas API；沙箱 | 可做跨端 Canvas shim | 中高（无 I/O） | 中（每次 draw 过 JNI） | 社区 / 需要预览 |
| WebView Canvas / WebGL | 完整 HTML5 | WebView2 可预览 | 中（JS 桥 / CSP） | 车机 WebView 待验证 | 社区 / 复杂 UI |
| 编译进 App | 最高 | 完美 | 高 | 最高 | 少量内置特效 |

**最大的代价不是加载，是预览**：DEX 主题是 Kotlin/Java，WPF 制作器无法运行；作者只能 Android Studio + 真机 / 模拟器。你们现在的“WPF 制作器预览 + 场景时间线 + 静态审计”对 DEX 主题基本失效。

所以：

- 如果主题作者是**你 / 可信 Android 开发者**，且能接受真机预览：DEX 是合理的，性能 / 保真最好；
- 如果要做**社区 / 设计师生态**，或 WPF 预览是硬需求：应该做 **JS/WebView 的 Canvas API**，同一份代码在 WPF（WebView2）和车机（WebView）跑；代价是性能 / 合成 / API 适配；
- 也可以两层：DEX 只做你选定的高级主题，社区仍用 JSON/JS。

### 11.7 建议路线（先验证，再决定开放）

**P0（3–4 周，含 bench）｜证明可行**

- 定 API 规格（FrameState / ThemeHost / 两层 Canvas / events / lifecycle）；
- 宿主集成：两层 Canvas + nav/112 布局 + 30fps 帧循环 + 数据快照；
- **Bench（见 §12.4）**：模拟数据 + 帧单步 + 111/112 占位 + 日志；
- 第一方 DEX 插件移植“火焰双擎”：36 火舌 + 140 火星 + 双环 + 111 布局；
- 验收：1920×720@30fps、视觉接近内置、内存 / CPU 可接受、切换 100 次不崩。

**P1（1–2 周）｜只给可信作者**

- 签名 / 清单 / API 版本 / R8 keep / 生命周期 / 失败回退 / 示例 / 文档；

- 先在内部做 1–2 个主题，不开放下载。

**P2（决策点）｜是否开放**

- 如果 P0 的保真 / 性能达标，且作者是 Android 开发者 → 保持可信 DEX；
- 如果社区 / 预览是必须 → 用同一 API 做 JS/WebView 适配，DEX 只留内部；
- 如果 P0 达不到 30fps 或视觉差距大 → Canvas API 不够，评估 GL/Surface，不要继续堆 loader。

**P3（1–2 个月）｜硬化**

- 崩溃 / ANR / OOM / 超时 / 低内存 / 分辨率 / 副屏重连 / 版本升级矩阵；
- 安全评审：签名、密钥、目录权限、插件可访问的数据面；
- 性能基线：每帧预算、GC、Bitmap 上限、classloader 泄漏。

### 11.8 结论

- **你的方向成立**：内置“复杂效果”就是 Canvas 画的；把 Canvas + 数据 / 事件 + live 布局 + 生命周期开放出来，正好补上 JSON 引擎缺的那一层。
- **但它不是“给一个 Canvas”这么简单**：要分层、帧循环、状态 / 事件模型、直播流布局、生命周期、失败回退、安全边界。
- **推荐先做第一方移植验证**（火焰双擎），再决定是否开放；这比先写通用 loader 更能证明价值。
- **交付方式由作者决定**：可信 Android 作者 → DEX；社区 / WPF 预览 → JS/WebView；不要把未签名 dex 放进可分享主题目录。

## 12. 设计补充（2026-11-14）：帧循环、层序、高频状态、Bench

> 针对四点：1) 小游戏引擎式帧循环；2) 作者自设 111/112 层位置；3) 高频状态用帧快照；4) 安卓版 Bench / 模拟器预览是否可行。

### 12.1 帧循环：宿主拥有时钟，主题只实现 update / draw

**不要每个主题自己起循环。** 一个进程里多个 `Choreographer` / `Handler` / `Timer` 会抢 vsync、泄漏、在切主题后继续跑。宿主保留一个 `ThemeClock`，只驱动当前主题。

- 锚定到 `Presentation` 里的 root View：`root.postOnAnimation(...)` / `postInvalidateOnAnimation()`；不要直接 `Choreographer.getInstance()`（它跟线程 / 默认屏走，副屏 vsync 可能不一致）。副屏是否稳定要在车机上实测，必要时用 `Display.getRefreshRate()` + `Handler` 兜底。
- 30fps 上限：60Hz 屏隔帧渲染，30Hz 屏每帧渲染；用 `elapsed >= 33ms` 判断，不要假设屏幕刷新率。
- 回调拆成 `onUpdate(frame)` + `onDraw(canvas, layer, frame)`：
  - `onUpdate` 每帧一次，推进粒子 / 物理 / 动画；
  - `onDraw` 每个 Canvas 层一次，只读 `FrameState`，不改状态；
  - 两层 Canvas 不会让模拟跑两遍。
- `dt`：单调时钟（`SystemClock.elapsedRealtimeNanos`），clamp 0–50ms；attach 后第一帧 dt=0；切主题 / 恢复时重置，避免时间跳变。
- 固定步长可选：`accumulator` + 最多 3 次 `onUpdate(1/30)`，`onDraw(alpha)` 插值；v1 可先用可变 dt，粒子不稳定再加。
- 暂停 / 恢复：`onAttach` / `onDetach`、`onVisibilityChanged`、Activity `onPause/onResume`、Presentation dismiss；停回调、停帧、让主题停后台线程。
- 帧预算：33ms；`onUpdate+onDraw` >16ms 警告，连续 >N 帧降级 / 禁用；主线程回调无法抢占，只能测量 + 回退。
- 每帧不分配：`FrameState` 复用 / 不可变；`Paint` / `Path` / 数组复用；Bitmap 在 attach 预加载。
- “小游戏引擎”的边界：给资源 / 位图缓存、数学 / 噪声 / 缓动、粒子池、文本度量即可；不要做场景图、输入系统、音频输出、物理引擎——主题不需要，也会把 API 拖死。

### 12.2 层序：可以，但用 slot stack，不要让作者摸 View

先区分两件事：

- **z-order / 层序**：111/112 在 Canvas 前面还是后面；
- **layout**：111/112 的 x/y/大小/缩放。

两者都可以开放，但方式不同。

**z-order：声明式 slot stack。** 宿主只创建固定几个 slot：

```text
canvas0（背景） / nav111 / card112 / canvas1（前景）
```

默认顺序：

```text
canvas0 < nav111 < card112 < canvas1 < MCU（固定最上）
```

作者在主题清单 / 初始化时给一个排列，例如：

```json
"stack": ["canvas0", "nav111", "canvas1", "card112"]
```

宿主校验：slot 必须存在、不能重复、MCU 不能参与排序；然后按顺序绘制。这样能表达：

- 火焰在 111 后面、HUD 在 111 前面；
- 112 在 111 上 / 下；
- 111 在 Canvas 上 / 下（作者自己决定）。

**实现注意（很重要）：**

- 111/112 是 `TextureView`；用 `removeView` / `addView` 或 `bringToFront` 改层序可能触发 detach/attach，**SurfaceTexture 会被销毁重建，视频黑一下**。用自定义 `ViewGroup` 的 `setChildrenDrawingOrderEnabled(true)` + `getChildDrawingOrder()` 改绘制顺序，不改变 view 树结构；
- 不要依赖 `View.setZ()` 改绘制顺序；它主要影响 elevation / 阴影，不保证 child draw order；
- 层序变化只在主题 attach / 参数变化时做，不要每帧重排；如果必须动画，改 drawing order 而不是 detach；
- 111/112 的 alpha、visibility 可以开放；任意 `clipPath` 不行（TextureView 不是普通 Canvas），v1 只支持 rect / 圆角 / 圆（`ViewOutlineProvider`）；
- 超过 2 层 Canvas 不建议：每层都是全屏 overdraw，1920×720@30fps 很快就会吃满 GPU/CPU。

**layout：**

- 111：`setNavTransform(x,y,scale)` 用于动画（便宜）；`setNavRect(l,t,w,h)` 只用于偶发尺寸变化（可能触发 Surface 重配 / 黑帧）；
- 112：固定比例 480×200，`setCard112Transform(x,y,scale)`；改 width/height 无效；
- 宿主只拒绝 `NaN` / `Infinity` / 非法 slot；**不按“合理位置”或安全区 clamp**（默认允许越界、滑出、负坐标），是否 clamp 由主题参数决定；
- 缺失时给 `available=false`，作者画 fallback；
- 改变 111 的显示尺寸可能让 CarPlay 重新协商 / 裁切；尽量用 transform，不要每帧 resize。

**层序语义：作者负责，宿主不做审美 / 安全裁判**

- 层序是创作的一部分：作者可能故意让 111 在 Canvas 后面（火焰包住导航）、让 112 压在 111 上、或用全屏过渡暂时盖住导航。宿主默认照做，**不强制 nav 置顶、不纠正“看起来不对”的顺序**。
- 宿主只保证**结构合法**：slot 存在、不重复、不含 MCU；值有限；`stack` 能应用；TextureView 不因重排被 detach；否则才是宿主的责任。
- MCU 层固定最上：这是硬件 / 系统层，不是宿主策略，作者也无法改。
- 导航被完全遮挡、111/112 被移到屏幕外、层序动画导致黑帧：这些属于作者选择；bench 给出诊断 / 警告（例如“navActive 但 nav 可见面积为 0”），但不阻止。
- 发布策略与运行时分开：可信签名主题由作者 / 审核负责；如果未来开放社区，再用签名 / 审核 / 用户确认 / 安全标记处理，不要靠运行时偷偷改作者的 stack——既不可靠，也限制创意。

### 12.3 高频状态：确认“帧快照 + 边缘事件”

- `ThemeData` 每帧采一次，不可变；数据源写 volatile 快照，宿主每帧读一次，不加锁；
- 速度 / 转速 / 频谱 / 电平只进 `FrameState`，不发事件；
- 导航开始 / 结束、歌曲切换、播放 / 暂停、昼夜、档位变化、节拍发 `onEvent`；队列有界、带 sequence、可丢旧；
- 频谱 16 段每帧拷贝到复用数组，不分配；不要每个 PCM buffer 回调；
- 封面用事件传 `Bitmap`（宿主解码 / 缓存 / 回收），不要每帧 decode；
- 不可用给 `NaN` / `available=false`；作者不要用 0 代替“没数据”；
- `onDraw` 纯函数；所有状态变更在 `onUpdate` / `onEvent`。

### 12.4 Bench：可行，而且是 DEX 路线的前提

**结论：可行，建议早做。** 一个独立的 debug Android app（或主 app 的 debug activity）就够，不需要重做一套渲染器。

功能：

- 1920×720 画布，按屏幕缩放显示；可选 1280×480 等面板；
- 111/112 用测试视频 / 动态图案占位，支持显示 / 隐藏、z-order、位置 / 缩放；
- 数据模拟：速度 / 转速滑杆、档位、续航 / 里程、昼夜、转向 / 双闪；导航开始 / 更新 / 结束；歌曲名 / 歌手 / 封面；16 段频谱 / 节拍；
- 时间线：`t=0 speed=0, t=5 speed=120 ...` 播放 / 暂停 / 单步；事件点；
- 帧控制：暂停、单步、时间缩放、FPS / 帧耗时 overlay；
- 日志 / 异常 / API 版本 / 签名 / 清单检查；
- Reload：DEX 无法卸载，重启 activity / process（bench 可以 force-stop）；脚本可热重载；
- 截图 / 录屏 / 黄金图：固定帧 `PixelCopy` 截图，和基线比；性能用 `gfxinfo` / Perfetto；
- adb：`push` 主题包、`am start` 指定主题、`screencap` 给 WPF 制作器做预览图；WPF 可以“推送 + 启动 bench + 抓图 / scrcpy”，但嵌入实时渲染还是要 Android 窗口。

复用现有 bench：

- `BenchCluster` / `BenchClusterReceiver` 已经有 adb 广播（cluster/swipe/lamp/theme/data/vehicle/demo info）；
- `CarDataMonitor` 已有 bench speed/rpm override；
- `BenchMcuView` 已经模拟 MCU 层；
- 新 bench 可以复用这些入口，只把“数据源”换成 bench provider。

限制：

- 模拟器性能不代表车机（GPU/CPU/发热），性能验收必须真机；
- 动态加载 dex 的断点调试要先验证（Android Studio attach + 源码映射），不行就靠日志；
- 没有热重载，改代码要重新打包 / 重启；脚本路线才有热重载；
- 模拟数据会掩盖真车 NaN / 时序 / 断连问题，bench 要能注入“不可用 / 断连”。

工作量：基础 bench 1–2 周；带时间线 / 黄金图 / 性能面板 2–3 周；不含主题模板 / 文档。

## 13. 插件主题：独立目录与元数据（2026-11-14）

> 结论：**这个拆分是对的。** 插件主题不要写进 `theme.json`，不要复用 `CustomThemeRepository`/`CustomThemeSpec`；单独目录、单独 manifest、单独 loader。设置页只读元数据做列表，选中时才加载/执行插件。两者在 UI 上都叫“自定义主题”，但在数据/加载层是两条管线。

### 13.1 目录

```text
files/plugin-themes/                 # 独立根目录，可配置
  flame_dual_ring/                   # 一个插件主题一个子目录
    plugin.json                      # 固定名称的元数据（不是 theme.json）
    plugin.dex                       # 主插件（D8 产物）
    assets/                          # 插件自己的图片/字体/数据
      ...
    SIGNATURE                        # 可选：对 manifest+dex+assets 的签名
```

- 根目录默认 `files/plugin-themes/`，与 JSON 主题的 `files/themes/` 平级；不要让两个 scanner 扫同一个目录。
- 每个子目录必须有 `plugin.json`；没有就忽略（不报错）。
- `plugin.dex` 是主插件；资源放 `assets/`。v1 不支持 Android XML 资源（`R.layout`/`R.drawable`），只能读 raw 文件。
- 分发可以用目录（和现在 JSON 主题一样 push），也可以以后打包成 `.dplugin` zip；目录模式要有“临时目录 + 校验 + 原子 rename”，避免推到一半被扫到。

### 13.2 `plugin.json` 示例

```json
{
  "schema": 1,
  "kind": "plugin-theme",
  "id": "flame_dual_ring",
  "name": "火焰双擎 · 插件版",
  "author": "jiuyueji",
  "version": "1.0.0",
  "description": "Canvas 重绘的火焰双环",
  "apiVersion": 1,
  "minHostCode": 42,
  "minHostName": "0.2.27",
  "entryClass": "com.example.flame.FlameTheme",
  "pluginFile": "plugin.dex",
  "panel": [1920, 720],
  "capabilities": ["canvas", "nav111", "card112", "events"]
}
```

字段语义：

| 字段 | 作用 | 注意 |
|---|---|---|
| `schema` | manifest 格式版本 | 先校验；未知版本拒绝 |
| `kind` | 固定 `plugin-theme` | 防止和 JSON 主题混淆 |
| `id` | 稳定唯一 id | 与 JSON 主题 id 可能冲突；选择/持久化要带 type 或前缀 |
| `name` / `author` / `version` | 设置页显示 | 不要用于安全判断 |
| `apiVersion` | 插件 API 版本 | 宿主只支持 1；不匹配拒绝 |
| `minHostCode` / `minHostName` | 最低宿主版本 | 用 versionCode 判断，versionName 只显示 |
| `entryClass` | **真正要加载的主类** | “主插件名称”在技术上就是它；不要只写显示名 |
| `pluginFile` | dex/apk 相对路径 | 禁止 `..`/绝对路径；大小上限 |
| `panel` | 设计面板 | 默认 1920×720；用于 bench/缩放 |
| `capabilities` | 声明用到 canvas/nav111/card112/events | 便于 UI/兼容性提示，不是权限系统 |

### 13.3 加载流程

1. **扫描**：只读 `plugin.json`（限大小），解析、校验字段、检查文件存在；不加载 dex、不执行插件。
2. **列表**：生成 `PluginThemeEntry`（id/name/author/version/status/type）；设置页把 JSON 主题和插件主题合并展示，带类型徽标。**不需要主题封面/缩略图**——设置页本来就不显示封面，列表只用文本（名称/作者/版本/类型/兼容状态）。
3. **选中**：校验签名/哈希 → 检查 `apiVersion`/`minHostCode` → 复制 dex 到 `codeCacheDir/plugin-themes/<id>-<hash>/`（或 `InMemoryDexClassLoader`）→ `DexClassLoader` → `loadClass(entryClass)` → `isAssignableFrom` → 实例化 → `attach`。
4. **切换走**：`detach` → 移除主题 View → 停帧循环 → 停插件线程；classloader 按 `id+version+hash` 缓存，不卸载；更新插件版本要重启 App 或接受泄漏。
5. **失败**：签名错/版本不匹配/类找不到/attach 抛异常 → 不切主题，回退到上一个主题或默认主题，设置页显示错误；不要留下黑屏/半个主题。
6. **主题切换门**：沿用现有 `ThemeSwitchGate`/遮罩；插件加载可以放后台线程，但 `attach`/View 操作回主线程；加超时（例如 3–5 秒），超时回退。

### 13.4 统一目录 / 选择 / 持久化

- 建议引入 `ThemeRef(type, id)`（`json` / `plugin`），或者在选择 id 上加前缀（`plugin:<id>`）；不要只用裸 id，否则两套主题 id 撞车。
- 设置页列表：同一个“自定义主题”区块，条目带“JSON / 插件”徽标；作者/版本/兼容状态；不兼容的置灰并说明原因。
- 两指左右切换：先把内置主题 + JSON 主题 + 插件主题合成一个 `selectionIds`；插件加载失败时跳过/回退，不能卡死在切换门里。
- 持久化：保存 `type+id`；旧版本只存 JSON id 的，迁移为 `json`；插件被删除时回退默认主题，不要崩。
- WPF 制作器：JSON 主题和插件主题用两个目标目录/两个推送按钮；插件主题还需要“构建 dex”的 Gradle/模板，WPF 不能直接编译 Kotlin/Java。

### 13.5 安装、签名、原子性

- **签名**：元数据本身不可信；`SIGNATURE` 必须覆盖 `plugin.json + plugin.dex + assets`（ECDSA/RSA，宿主内置公钥）；设置页显示“已验证/未验证”，发布版拒绝未验证。
- **原子性**：WPF 先推到 `plugin-themes/.staging/<id>/`，校验通过后 `rename` 成 `<id>/`；或者推 `.dplugin` zip，App 解压到临时目录再 rename。避免扫到半个目录。
- **路径安全**：`pluginFile`/资产名拒绝 `..`、绝对路径、符号链接；限制单文件/总大小。
- **目录权限**：`plugin-themes/` 700；不要 `chmod -R 777`；WPF 用 root/adb 写默认目录，或写到外部目录后由 App 复制+校验。
- **不加载未签名**：开发期可以在 debug/bench 放行，release 必须签名；不要用“文件名/作者”当信任。

### 13.6 不要做的事

- 不要在 `theme.json` 里加 `type:"plugin"` 或插件字段——那会把两套 schema 绑死。
- 不要用 `theme.json` 作为插件目录的元数据文件名——现有 JSON scanner 会误读；固定用 `plugin.json`。
- 不要在设置页为了显示条目而 `DexClassLoader`/执行插件——列表只读元数据；要看动态效果就跑 bench。
- 不要把 JSON 主题和插件主题混在同一个根目录/同一个 scanner。
- 不要让插件主题和 JSON 主题共享裸 id 命名空间。
- 不要跳过 `apiVersion`/`minHostCode` 检查；release 的 R8 可能让旧插件直接 `NoSuchMethodError`。
- 不要把未签名插件放进可分享目录；不要给插件目录 777。

### 13.7 工作量

| 项 | 人日 |
|---|---|
| manifest/repository/设置页列表（只读元数据） | 2–3 |
| loader/签名/API 版本/失败回退 | 5–10 |
